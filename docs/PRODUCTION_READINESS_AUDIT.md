# MOMENTO production readiness audit

**24 November 2026 · Phase 00 · Release decision: hold public intake.** The four service pages, shared selection, checkout and Telegram transport already exist. The decisive gap is what the business receives. For a photobook the browser carries finishing choices that the operator cannot recover from the Telegram message. The endpoint also accepts the browser's price, supplies its own affirmative consent and has a success path that sends nothing. A working build or bot token alone cannot close these gaps.

## What survives the customer journey

1. **Discovery and configuration.** `useBoothOrder` and `usePhotographyOrder` restore their single service position. `useSelection.put` asks before replacing a different one. Ready zones key by concept and custom zones share one notes item. Books key by local project ID, allowing several books and copies. The photography “photobook” extra is an expression of interest and creates no configured book. Clarify this when both appear in one request.
2. **Price.** `app/lib/selection.ts` builds human-readable rows plus service config. Booth and custom zones have null prices. Photography sums a known package and known extras and marks outstanding extras. A null base discards any known extra amount from the displayed sum in both photography and ready zones. `useCart.total` sums unit price × quantity and retains quote/demo flags. Books currently use demo estimates. No server catalog reconciles these snapshots. Rebuild old cart items against active approved terms and show changed estimates for customer review.
3. **Persistence.** `useCart.ts` uses localStorage v2, migrates v1, filters malformed/duplicate positions, expires after 30 days from recorded activity and reloads across tabs. `cart.client.ts` defers the first load until after hydration. `useRequestDraft.ts` stores event/contact plus sending key and content fingerprint, with a 30-day lazy expiry. Consent resets on reload. Draft writes debounce 400 ms. Storage quotas and disabled storage can lose data: `mutate` re-reads storage before every change and `readStoredCart` treats a failed read as empty. Test in-memory continuation. Read/modify/write across tabs is not atomic.
4. **Event and validation.** One optional date, time, type, duration, venue and wishes for the whole inquiry. Checkout prefills the booth type once. Edits can leave two different event types in the item and request. Name, phone (10–15 digits), preferred channel, conditional Telegram/email and consent are checked in the UI. Date validation checks shape and lexical ordering, accepts impossible calendar dates and uses different “today” boundaries (browser today, server yesterday). Agree a business timezone and apply calendar/time validation on both sides. A date expresses a preference only.
5. **Checkout and response.** `pages/checkout.vue` maps snapshots to `LeadItem[]`, adds a key, consent timestamp, honeypot and full route path, then calls `submitLead`. A pending guard disables repeat submit. Server field errors appear inline. Failure keeps state, success clears the entire current cart/draft and shows a number and manual-confirmation copy. A later tab edit or typing during the outstanding request can be cleared by an older response. Keep a submitted snapshot and clear only acknowledged positions/versions and matching draft.
6. **Operator handoff.** `leadMessageBlocks` renders client display rows plus a book project ID, with no operator lookup for a browser-local project. The book snapshot includes endpaper, title finish/position, spine and extras that never reach the operator. Custom zone details cut notes to 90 characters while full `config.notes` never gets rendered. Server silently slices the cart to 30 positions regardless of the client’s full count. Reject unsupported sizes before delivery and surface field errors without discarding items.

## Minimum viable Telegram delivery design

**Implemented.** `nuxt.config.ts` and `.env.example` define private `NUXT_TELEGRAM_BOT_TOKEN` and `NUXT_TELEGRAM_CHAT_ID`. The optional API base supports a local stub. The form posts same-origin JSON. `server/api/leads.post.ts:44` checks declared length. `sanitizeLead` filters/coerces values and limits strings. The handler checks fields, uses a 24-hour process-memory map for pending/completed keys, sends sequential HTML messages with a 10-second timeout per part, returns 503 if unconfigured and 502 on transport failure. The client aborts at 30 seconds. Server-generated numbers identify attempts. User-supplied display strings are generally escaped.

**Defects to close.** `server/utils/leadMessage.ts:67` constructs positive consent and `server/api/leads.post.ts:51` validates a literal true. Line 55 acknowledges a filled honeypot without transport. Item price, labels, quote flags and arbitrary config survive sanitization. The body guard relies on a header rather than enforcing bytes consumed. No rate limiter, hard cache capacity or payload binding. The formatter clips oversized formatted blocks, which can lose selections or break markup. An upstream rejection logs its description. `useRequestDraft.keyFor` can reuse a key for edited content after a network failure, returning an earlier success for different choices. Failed in-flight waiters may each fall through into a new send. Retries after a partially accepted multipart delivery can create duplicates under a new number.

**Proposed contract and processing order.** Retain the one endpoint and `#shared/lead`. Keep higher-volume artwork and actual photos out of the commercial inquiry.

| Field group | Minimal trusted representation |
|---|---|
| Envelope | Client-generated random submission key stable for one immutable payload, schema version, bounded items, optional event, contact and affirmative consent with notice version. Server assigns receipt time and stable reference for the attempt. Use a fixed source path. |
| Items | Service discriminator, stable position ID, quantity, allowlisted config fields. Booth event/design IDs. Photography direction/package/available extra IDs. Ready zone concept/options or bounded custom brief. Book format/pages/cover/colour/title/finish/position/spine/paper/endpaper/allowed extras/copies and layout status, plus optional local reference. Derive display labels and dimensions on the server. |
| Event and contact | One optional real calendar date and local time for the whole event, optional venue/duration/wishes. Name, phone, selected channel and only the relevant channel identifier. Minimize free text and enforce field, item and whole-request bounds. |
| Prices | Share pure catalog data/calculation between app and Nitro. Validate available combinations, units, quantity and current catalog revision. Recompute fixed prices in RUB and distinguish partial/quote-only totals. Reject invalid inputs. If the customer's displayed term has changed, return a review-required response before sending. |

1. Serve over HTTPS. Configure secrets in the Node host. Fix the production Bot API origin to the official HTTPS host, reserve overrides for explicit local testing and keep tokens, chat and Bot API URLs out of client config, error bodies and logs.
2. Check JSON type and actual streamed bytes at ingress/before parsing, plus per-field/array bounds. Enforce a small bounded per-source and process-wide rate budget and concurrent-send limit before expensive work. Trust forwarded addresses only from the configured proxy. Use short-lived keyed identifiers for limits. Return 413 or 429 with retry guidance and no success receipt. Reject a filled honeypot without acknowledging delivery. Verify actual consent and notice version before forwarding.
3. Normalize the immutable request and bind its digest to the key. A pending duplicate joins the same result, including failure. A completed identical retry returns the same receipt within the TTL. Same key/different content returns 409 and prompts review. Bound map size and TTL without evicting in-flight work to admit new sends. Retain a stable support reference for uncertain outcomes, including restart reconciliation where feasible.
4. Prefer one bounded plain-text `sendMessage` with labelled business fields, no parse mode and disabled previews. Validate formatted length before transmission. A legitimate mixed cart too large for one message needs either a clear editable size error or bounded numbered parts, each with the same reference and part count. Never silently trim agreed options. Telegram limits text to 4,096 characters after entity parsing. [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)
5. Return 200 with the reference only after all required upstream acknowledgements. Use 400/422 for invalid data, 409 for changed terms/content, 503 for configuration or capacity problems, 502 for a definitive upstream refusal and an explicit uncertain result for timeout/lost acknowledgement. Keep the overall server deadline below the client deadline. Respect upstream backoff. Avoid automatic resending when receipt is uncertain. Record only reference, outcome class, part count, elapsed time and status code. Exclude raw upstream bodies, request URLs with tokens, contact fields, free text and IPs from logs.
6. Preserve draft and selection on every non-confirmed result. Display the reference and a monitored alternative contact, let customers retry the exact snapshot, and handle later edits as a separate confirmed revision. A successful message means Telegram accepted it. Reading, business recording, date confirmation and payment are separate events.

**Reliability boundary.** The Node process has no durable inbox, queue or transactional deduplication. Restarts, eviction, expiry and multiple instances remove or split its memory of deliveries. A timeout after Telegram accepts a message is indistinguishable from some failed sends. Multipart messages may arrive only in part. Browser data can be cleared or unavailable. No exactly-once, durable storage or guaranteed eventual delivery claim is supportable. Proposed launch assumption: one long-lived process with an owner monitoring a private group and a published fallback. Reassess hosting if that assumption changes. The manual recovery procedure is in the [checklist](PRODUCTION_CHECKLIST.md#manual-recovery).

**Owner/legal review.** Map browser drafts, project titles/captions, host and proxy, Telegram group/member devices and external business records. Confirm applicable personal-data processing, collection/localization, third-party and cross-border transfers, lawful grounds, notice/consent, access, retention and deletion for each location. Identify the operator and rights contact. Inventory any host logs/backups and planned tracking. If this particular processing route cannot be approved, pause public intake and return the architecture decision to the owners. The audit makes no legal determination.
